## 一、传输层

### 1.1 连接建立

```
BootConfig（启动参数 --la/--ua 解出）
  ├── BattleServerIp        qd183.ssjj.abd007.com
  ├── BattleServerTcpPort   1810
  ├── BattleServerUdpPort   1960
  ├── RoomId                135904415577192
  ├── CharId                1000725282123
  ├── Timestamp             1792834702471
  └── Sign                  4710d7407d822f5439d8fc9d3e7d9329
        ↑ 登录服签发，客户端只转发（ConnectToServerUtility.cs:61）
```

建立流程（`ConnectToServerUtility.Connect()`）：
1. `IBattleServer.Connect(ip, tcpPort, udpPort, 0, true)`
2. TCP 连上后 → `SendTcpMessage(2, LoginData{RoomId, UserId, Timestamp, Sign, LoginType=1, NpGray})`
3. 服务端回 method **1** `CallBackLoginData`
4. 服务端发 method **1000**（`ConnectionIDHandler`）→ 拿到 connectionId（实测 -646）
5. `SendP2PPackageSystem` 发 P2P 连接 → UDP 绑定 → `P2PDataHandler` 确认
6. 之后 TCP 走控制/事件，UDP 走快照

### 1.2 TCP 帧格式

```
+--------+---------------------------+
| len:4B | APC protobuf              |
|  big   | { 1: methodId(varint)     |
|  endian|   2: content(bytes) }     |
+--------+---------------------------+
```

实测样本：
```
00 00 00 18 | 08 42 12 14 08 37 10 33 18 d0 0f 20 d0 0f 50 5a 58 1e 60 0a 68 3a 70 3c
             ↑     ↑
        field1=66  field2(content,20B)
```
→ methodId=**66**，content = `{1:55, 2:51, 3:2000, 4:2000, 10:90, 11:30, 12:10, 13:58, 14:60}`

### 1.3 UDP 帧格式

**上行（客户端→服务端，实测 42~52 字节）**
```
+--------+-----------+--------+--------+-----------+----------+
| len:4B | connId:4B | type:1 | seq:2  | timestamp | UserCmd  |
|        | (= -646)  |        |        |  :4       | 变长     |
+--------+-----------+--------+--------+-----------+----------+
```
实测：`00 00 00 26 | ff ff fd 7a | 02 | 42 00 | 00 81 a7 | 00 03 e9 4c | ...`
- connId `fffffd7a` = -646（补码，与 TCP 的 ConnectionIDHandler 一致）
- seq `81a7` 递增 → `81a8` `81a9` `81aa`…
- timestamp `0003e94c` 递增

**下行（服务端→客户端，实测 158~164 字节）**
```
+--------+--------+--------+-----------+------------------+
| len:4B | type:1 | seq:4  | timestamp | protobuf 快照    |
+--------+--------+--------+-----------+------------------+
```
实测：`00 00 00 9a | 01 | 00 00 09 b1 | 01 00 00 00 | 00 00 00 00 4c 5a 34 f2 | 25 00 44 b0 13 64 | 01 01 0b | 22 30 ...`
- type `01` = 快照
- type `02` / `03` = 其他下行（增量/事件）
- 尾部 protobuf 可直接认出 `PlayerEntityData` 字段

## 四、UDP 快照数据模型

下行 protobuf 里直接可识别的结构（实测样本解析）：

```
#4(48B):                      ← 某个容器
  #2(46B):
    #1=v1
    #2(10B): {#1=0, #55=127758, #59=1}      ← PlayerEntityData: X / 某字段
    #2(10B): {#1=1, #55=126941, #59=1}
    #4(8B):  {#1=2, #55=0, #59=1}
    #5(8B):  {#1=3, ...}
```
字段号 55/59 等与 `NetData.PlayerEntityData` 的 protobuf 定义一一对应，可用 `NetData.dll` 反序列化还原。

## 五、对 LoopbackBattleServer 的意义

要实现"所有模式"的服务器逻辑，不需要 268 个全做，按这个顺序：

**第一批（能进图）**：1 → 3 → 12 → 111 → 119 → 125 → 61 → 232
**第二批（能动/能打）**：24（武器槽）→ 8（UserCmd 回放）→ 131（命中回包）→ 20（伤害）
**第三批（能结算）**：13（回合）→ 66/67（经验）→ 17（MVP）→ 4/5（胜负）
**第四批（按模式）**：14/16（爆破）、23/25（生化）、64/65（大头）、133-135（投票）…
